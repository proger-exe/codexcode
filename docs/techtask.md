# ТЗ: `codex-code`

## IDE поверх `codex-cli` в стиле Cursor

## 0. Суть проекта

`codex-code` — это desktop/web IDE-оболочка поверх `codex-cli`, которая превращает CLI-агента в нормальную визуальную среду разработки: редактор кода, боковой чат, inline-правки, открытие файлов по цитатам, шаблоны `AGENTS.md` и генерация структуры репозитория.

База: OpenAI Codex CLI уже является open-source CLI coding agent, который локально читает, изменяет и запускает код в проекте. То есть фундамент есть, человечество не обязано снова изобретать колесо, только прикрутить к нему монитор, чат и UX без боли. ([OpenAI Help Center][1])

Codex также использует `AGENTS.md` как способ задавать инструкции агенту внутри репозитория, поэтому шаблоны `AGENTS.md` логично сделать не “доп. фичей ради галочки”, а частью создания проекта. ([GitHub][2])

---

# 1. Цель

Создать IDE-подобную среду `codex-code`, которая:

1. Позволяет работать с кодом через интерфейс, а не только через терминал.
2. Использует `codex-cli` как агентный backend.
3. Даёт Cursor-like UX:

   * выделил код → спросил/изменил;
   * получил цитату файла → кликнул → открыл файл;
   * получил diff → применил/отклонил;
   * общаешься с агентом в боковом чате.
4. Ускоряет создание репозиториев через шаблоны:

   * `AGENTS.md`;
   * архитектурные пресеты;
   * стартовые структуры проектов.

# 3. Основные сценарии пользователя

## 3.1. Открытие проекта

Пользователь открывает папку проекта.

Система:

1. Проверяет наличие `.git`.
2. Проверяет наличие `AGENTS.md`.
3. Проверяет доступность `codex-cli`.
4. Индексирует дерево файлов.
5. Показывает редактор, файловое дерево и боковой чат.

Если `AGENTS.md` отсутствует, система предлагает создать его из шаблона.

---

## 3.2. Уточнение фрагмента кода

Пользователь выделяет код в редакторе и вызывает действие:

* “Объяснить”
* “Найти проблему”
* “Упростить”
* “Оптимизировать”
* “Покрыть тестами”
* “Переписать под архитектуру проекта”
* “Задокументировать”

Система отправляет в `codex-cli` контекст:

```text
Файл: path/to/file.py
Диапазон: L10-L42
Выделенный код:
...
Задача пользователя:
...
```

Ответ отображается в боковом чате или inline-блоке рядом с кодом.

---

## 3.3. Редактирование в том же окне

Пользователь просит:

> “Переделай этот сервис под repository pattern”

Система:

1. Передаёт запрос агенту.
2. Получает предложения изменений.
3. Отображает diff.
4. Даёт кнопки:

   * Apply
   * Reject
   * Apply selected hunks
   * Ask follow-up
5. После применения обновляет файл в редакторе.

Никакого “скопируй этот код руками, смертный”. Мы уже пережили каменный век, вроде бы.

---

## 3.4. Открытие файлов из цитаты

Если агент отвечает:

```text
Проблема находится в src/services/user_service.py:42
```

или:

```text
См. app/api/routes.py lines 10-25
```

IDE должна распознать цитату как ссылку.

При клике:

1. Открывается файл.
2. Курсор прыгает на нужную строку.
3. Строка подсвечивается.
4. Если указан диапазон, подсвечивается диапазон.

Поддерживаемые форматы:

```text
src/main.py
src/main.py:10
src/main.py:10-25
src/main.py#L10
src/main.py#L10-L25
`src/main.py`
[ src/main.py:10 ]
```

---

## 3.5. Боковой чат

Боковой чат — главный интерфейс общения с агентом.

Функции:

1. Отправка сообщений.
2. Прикрепление:

   * текущего файла;
   * выделенного фрагмента;
   * нескольких файлов;
   * diff;
   * ошибок из терминала;
   * результатов тестов.
3. История чата внутри проекта.
4. Кнопки быстрых действий:

   * Explain file
   * Review file
   * Generate tests
   * Refactor selection
   * Fix error
   * Summarize project
   * Update AGENTS.md

# 4. Функциональные требования

## 4.1. Редактор кода

### Требования

Редактор должен поддерживать:

1. Открытие файлов из дерева проекта.
2. Подсветку синтаксиса.
3. Нумерацию строк.
4. Выделение диапазона кода.
5. Inline-actions над выделением.
6. Применение diff-изменений.
7. Автосохранение или ручное сохранение.
8. Отображение изменённых файлов.
9. Базовый поиск по файлу.

### Рекомендуемая реализация

Frontend editor:

```text
Monaco Editor
```

Причина: это база VS Code, а значит, меньше боли. Не ноль, конечно, потому что в разработке ноль боли бывает только в рекламных буклетах.

---

## 4.2. Файловое дерево

### Требования

Файловое дерево должно:

1. Показывать структуру проекта.
2. Исключать мусор:

   * `.git`
   * `node_modules`
   * `.venv`
   * `dist`
   * `build`
   * `__pycache__`
3. Позволять:

   * открыть файл;
   * создать файл;
   * создать папку;
   * переименовать;
   * удалить;
   * скопировать путь;
   * вставить путь в чат.

---

## 4.3. Интеграция с `codex-cli`

`codex-code` не должен переписывать мозг агента. Он должен быть оболочкой.

### Слой интеграции

Нужен модуль:

```text
CodexAdapter
```

Ответственность:

1. Запуск `codex-cli`.
2. Передача prompt/context.
3. Получение streaming-ответа.
4. Парсинг:

   * текста;
   * цитат файлов;
   * diff;
   * команд;
   * ошибок.
5. Управление сессиями.
6. Обработка approval-flow.

### Варианты интеграции

#### MVP-вариант

Запуск через subprocess:

```text
codex [args]
```

Плюсы:

* быстрее реализовать;
* меньше зависимости от внутренностей Codex;
* проще отлаживать.

Минусы:

* парсинг вывода может быть грязным;
* меньше контроля;
* CLI может поменять формат вывода, и всё радостно посыпется, как обычно.

#### Более правильный вариант

Использовать SDK/внутренний API, если он стабилен.

Плюсы:

* чище архитектура;
* лучше streaming;
* меньше парсинга.

Минусы:

* выше зависимость от текущей реализации Codex.

## 5.2. Рекомендуемый стек

### Вариант A: Desktop-first

```text
Tauri + React + TypeScript + Monaco Editor
```

Плюсы:

* легче, чем Electron;
* нормальный доступ к файловой системе;
* приятнее для desktop IDE;
* Rust backend можно использовать для процессов, файлов и безопасности.

Минусы:

* Tauri сложнее, чем “накидать Electron и молиться”.

### Вариант B: Быстрый MVP

```text
Electron + React + TypeScript + Monaco Editor
```

Плюсы:

* быстрее собрать;
* много готовых решений;
* проще найти разработчиков.

Минусы:

* жрёт память как браузер, потому что это и есть браузер в плаще.

### Рекомендация

Для MVP:

```text
Electron + React + TypeScript + Monaco
```

Для production:

```text
Tauri + React + TypeScript + Monaco
```

# 7. Шаблоны `AGENTS.md`

## 7.1. Цель

Дать агенту стабильные инструкции по проекту.

Файл `AGENTS.md` должен описывать:

1. Назначение проекта.
2. Стек.
3. Архитектурные правила.
4. Стиль кода.
5. Команды запуска.
6. Команды тестов.
7. Команды линтера.
8. Что нельзя менять без разрешения.
9. Как оформлять изменения.
10. Как агент должен отвечать.

---

## 7.2. Типы шаблонов

### 1. Minimal

Для маленьких проектов.

```text
AGENTS.md
README.md
src/
tests/
```

### 2. Python Backend

Под FastAPI / SQLAlchemy / Alembic / pytest.

```text
app/
  api/
  core/
  domain/
  services/
  infrastructure/
tests/
alembic/
AGENTS.md
```

### 3. TypeScript Frontend

Под Vue/React.

```text
src/
  components/
  pages/
  shared/
  entities/
  features/
  app/
AGENTS.md
```

### 4. Fullstack

Frontend + backend.

```text
apps/
  web/
  api/
packages/
  shared/
AGENTS.md
```

### 5. Bot / Automation

Для Telegram-ботов, воркеров и автоматизации.

```text
app/
  bot/
  handlers/
  services/
  domain/
  infrastructure/
  workers/
AGENTS.md
```

### 6. DDD Monolith

Для нормальных людей, которые уже поняли, что микросервисы без причины — это распределённый способ страдать.

```text
src/
  modules/
    users/
      domain/
      application/
      infrastructure/
      presentation/
  shared/
  bootstrap/
tests/
AGENTS.md
```

# 10. Работа с diff

## 10.1. Формат отображения

```text
File: src/services/user_service.py

- old line
+ new line
```

Кнопки:

```text
Apply file
Apply hunk
Reject file
Reject hunk
Open file
Ask about this change
```

---

## 10.2. Проверка безопасности

Перед применением diff:

1. Проверить, что файл не изменился с момента генерации diff.
2. Если изменился, показать конфликт.
3. Не перетирать изменения пользователя молча.
4. Сохранять backup/snapshot перед применением.

# 15. Критерии готовности MVP

MVP считается готовым, если:

1. Пользователь может открыть локальный проект.
2. Пользователь может открыть и редактировать файл.
3. Пользователь может выделить код и спросить Codex о нём.
4. Ответ Codex появляется в боковом чате.
5. Цитаты файлов кликабельны.
6. Diff от Codex можно применить.
7. `AGENTS.md` можно создать из шаблона.
8. Новый проект можно создать из архитектурного шаблона.
9. Все операции с файлами не ломают проект молча.
10. Ошибки Codex CLI отображаются понятно.

# 16. Нефункциональные требования

## 16.1. Производительность

Целевые показатели:

```text
Открытие проекта до 5k файлов: ≤ 3 сек
Открытие файла до 1 MB: ≤ 300 мс
Отправка выделения в чат: ≤ 200 мс до начала запроса
Клик по citation: ≤ 150 мс
Применение diff до 500 строк: ≤ 1 сек
```

---

## 16.2. Надёжность

Система не должна:

1. Молча перезаписывать файлы.
2. Применять diff к изменённому файлу без проверки.
3. Удалять файлы без подтверждения.
4. Зависать при ошибке Codex.
5. Терять историю чата при перезапуске.

---

## 16.3. Безопасность

Требования:

1. Не отправлять лишние файлы в контекст.
2. Уважать `.gitignore`.
3. Добавить `.codexignore`.
4. Показывать пользователю команды, которые агент хочет выполнить.
5. Не запускать опасные команды без approval.
6. Не читать `.env` без явного разрешения.

Пример `.codexignore`:

```text
.env
.env.*
secrets/
private/
*.key
*.pem
node_modules/
.venv/
dist/
build/
```

# 18. Главные риски

## 18.1. Нестабильность CLI-интеграции

Если `codex-cli` меняет формат вывода, парсер может ломаться.

Решение:

```text
CodexAdapter должен быть изолированным слоем.
```

Не размазывать вызовы CLI по всему приложению, иначе потом будет архитектурная каша, а не IDE.

---

## 18.2. Diff-конфликты

Агент может предложить diff к старой версии файла.

Решение:

```text
Перед apply сравнивать file hash.
```

Формула:

```text
canApply = currentHash === baseHash
```

Если `false`, показывать конфликт.

---

## 18.3. Слишком широкий MVP

Главная опасность — попытаться сразу сделать VS Code + Cursor + JetBrains + храм продуктивности.

Решение:

```text
MVP = editor + chat + citations + diff + templates
```

Всё остальное потом.
